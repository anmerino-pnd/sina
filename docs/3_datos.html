Datos e Ingesta

3.1. Fuentes de datos

Sina agrega tres familias de precios de consumo en México:

Categoría Fuente Técnica
Gasolina API de la CRE (Comisión Reguladora de Energía) requests (API de gobierno)
Gas LP API de la CNE (precios máximos de Gas LP) requests (API de gobierno)
Supermercados Sitios de Soriana, Del Sol, Benavides, Farmacias Guadalajara Scraping (navegador o servidor, según la tienda)
Volantes (secundario) Casa Ley (Publitas) Descarga de imágenes + anotación + OCR con LLM

Las gasolineras se llenan en dos fases: el scraping obtiene latitud/longitud y la API de la CRE completa los precios magna/premium/diesel. El Gas LP se guarda desnormalizado (IDs y nombres) para evitar JOINs.

3.2. Estrategia de caché inteligente

Cada categoría tiene su propia vigencia; el refresco es on-demand con stale-while-revalidate (datos vencidos se sirven de inmediato como cache_vencido y el refresco contra la fuente corre en background — ver flujo en Arquitectura) y hay un scheduler que precalienta los datos ya presentes.

Categoría Frecuencia Trigger
Gasolina Diaria (AM) Usuario busca + datos > 24 h
Gas LP Semanal (sábado) Usuario busca + datos > último sábado
Supermercados Programada (semanal opt-in) Scraping directo
Ubicaciones Una vez + updates Scraping inicial, luego solo cambios

Los modelos llevan métodos de vigencia (esta_vigente(), necesita_actualizacion()) apoyados en helpers de zona horaria de México (config/timezone.py).

3.3. Pipeline de ingesta

Los spiders de supermercados son dirigidos por base de datos: cada uno lee sus rutas activas de catalogos_config (vía CatalogoRepository.obtener_rutas_activas), arma cada URL como base_url + url_path, scrapea y hace upsert a supermercados. La URL base por tienda vive en config/credentials.py; los JSON de catálogo guardan solo el url_path.

Detalles por plataforma en Backend y API → Scrapers. El seeder (sina/db/seeder.py) es genérico: seed_catalogo_tienda(...) carga cualquier *_config.json (departamento → categoría → {url_path, prioridad}), y TIENDAS_CATALOGO lista todas las tiendas. El upsert de productos deduplica por pid de forma global, así que categorías o tiendas que se traslapan nunca crean filas duplicadas.

3.4.2. MongoDB (colecciones)

Mongo guarda lo documental que cambia en runtime y siempre con degradación suave: si el contenedor está caído, la app sigue (el chat sin historial, el selector de ciudades con la semilla del JSON, la auditoría como no-op). El chat usa paginación por punteros (detalle en Agente); los stores chicos viven en sina/db/stores.py.

3.5. Embeddings y búsqueda semántica

Cuando ENABLE_EMBEDDINGS=1 (solo PostgreSQL), upsert_productos invoca EmbeddingService.vectorizar_productos() en lote y puebla Supermercado.embedding. La búsqueda de productos combina filtro duro (tienda/departamento/categoría) con similitud vectorial (distancia coseno sobre pgvector), con fallback de texto (ILIKE) si no hay embeddings. El proveedor es perezoso y abstracto (EmbeddingProvider) con dos implementaciones elegibles por EMBEDDING_PROVIDER: ollama (default, qwen3-embedding:8b — mismo servidor Ollama que el chat/VLM, sin torch) y huggingface (sentence-transformers local). Modelo vía EMBEDDING_MODEL. Para (re)generar vectores de productos ya existentes (al activar embeddings tarde o cambiar de modelo): ENABLE_EMBEDDINGS=1 uv run python -m sina.embedder.backfill (--todos recomputa todo).

3.6. Criterio de precios (barato / promedio / caro)

Los tableros clasifican cada precio en Barato / Promedio / Caro (color en mapas, rankings y badges). El criterio es robusto a outliers y coherente:

  • Ancla = mediana del municipio (para el combustible/categoría consultado); ningún valor atípico la mueve.
  • Dispersión = MAD (desviación absoluta mediana) escalada a sigma robusta (1.4826 · MAD), con un piso relativo (0.8 % de la mediana) para que la banda no colapse cuando muchos precios son idénticos.
  • Clasificación por z-score robusto:
z = (precio − mediana) / escala        escala = max(1.4826 · MAD, 0.008 · mediana)
z ≤ −0.6745  → Barato
z ≥ +0.6745  → Caro
resto         → Promedio

El umbral 0.6745 equivale al rango intercuartílico de una distribución normal (± ese valor cubre el 50 % central), afinado con datos reales de Hermosillo. Ventajas frente al método anterior (partir el rango mín–máx en tercios): un solo outlier ya no recorre los umbrales de todos, y el mismo precio siempre recibe el mismo color. Con pocas estaciones (< 4) todo se marca como “Promedio” por datos insuficientes. La implementación vive en frontend/src/lib/precios.ts y la comparte Gasolina y Gas LP.

3.7. Pipeline de volantes (flyers) — recorte por zonas + VLM

Para tiendas cuyo sitio no es scrapeable, Sina extrae precios de sus volantes. El flujo recorta el flyer en zonas (paneles/bloques, no producto por producto: así el VLM recibe un “zoom” con texto legible y alucina menos), extrae cada zona con un VLM y, tras verificación humana, inserta a supermercados. La pre-anotación con CV clásico tiene dos modos por tienda (_PARAMS en annotator/zonas.py):

  • Paneles (Casa Ley): no busca espacios en blanco (los flyers de Ley usan paneles de color sin pasillos blancos anchos, que fundirían todo en un bloque) sino el inverso: detecta los pasillos —líneas claras largas— y propone los paneles que quedan entre ellos.
  • Bandas (Abarrey): su rejilla densa no tiene pasillos continuos (los empaques los interrumpen), así que se usa el perfil de blancura por fila: los renglones mayormente claros separan y cada tramo continuo no-blanco es una zona a lo ancho de la página (≈ una fila/departamento de productos, la granularidad ideal para el VLM).

Ambos son propuestas que el humano ajusta. Una perilla de fusión (Ninguna/Media/Alta) reagrupa cajas cercanas cuando la detección cruda sale fragmentada. Los volantes viven agrupados bajo datos/flyers/<tienda>/… para que el anotador liste solo tiendas de volantes.

Scrapers de volantes. casaley_spider (Selenium: el visor Publitas es JS dinámico) y abarrey_spider (curl_cffi + BeautifulSoup: ofertas.php es server-rendered; además extrae la vigencia de la página — vigencia_texto crudo y vigencia_inicio/fin en ISO parseadas de “Del 11 al 17 de Julio”, con manejo del cruce de año; si el texto no se entiende quedan en null, jamás se inventa una fecha). Ambos escriben la misma estructura datos/flyers/<tienda>/<ciudad>/<fecha>/page_NN.jpg + metadata.json.

Ciclo de vida y vigencia (sina/annotator/ciclo.py): cada etapa deja un artefacto en la carpeta del flyer — descarga (metadata.json), anotación (labels/), extracción (extraccion.json) y persistencia (persistido.json) — y de ahí se infiere el estado sin tabla nueva. La vigencia se resuelve por prioridad: la confirmada por el humano al insertar (persistido.json) → la parseada del scraping (metadata.json) → desconocida (el sistema no adivina: cada tienda maneja duraciones y días de vencimiento distintos). El panel “Folletos” del anotador (GET /api/v1/annotator/pendientes) muestra el flyer más reciente por tienda-ciudad con su etapa, vigencia y acción sugerida, y el modal de inserción precarga la vigencia desde metadata.json cuando existe.

Descarga automática (scheduler.py, opt-in ENABLE_FLYERS_SCRAPING): un monitor corre cada FLYERS_INTERVALO_MIN minutos (default 20); si la vigencia real conocida del flyer más reciente ya pasó, corre el spider. Si la tienda aún publica el mismo flyer (imágenes byte-idénticas), limpia la carpeta nueva y el siguiente tick reintenta — así una publicación tardía se captura a los minutos, no al día siguiente. Los ticks sin vencimientos solo leen metadatos del filesystem (costo despreciable).

Modelo de datos unificado. Los productos de flyer viven en la MISMA tabla supermercados que el scraping, con un discriminador fuente ("scraping" vs "flyer"). Como los flyer no traen pid (la clave del scraping), pid es nullable y el dedup de flyer es por la clave compuesta (tienda, producto, fuente, vigencia_inicio). Al ser promos temporales, llevan vigencia_inicio/fin; la búsqueda puede filtrar solo_vigentes para no mostrar ofertas vencidas. Cada cadena (Ley y Abarrey hoy) usa su propio modo/tuning de zonas y queda separada por tienda.

Dataset YOLO. Cada guardado del anotador exporta las cajas corregidas por el humano a labels_yolo/*.txt (coordenadas normalizadas, clase única zona). El consolidador sina/annotator/dataset.py (uv run python -m sina.annotator.dataset) barre todos esos labels, los empareja con su imagen y reconstruye datos/yolo_dataset/ en formato Ultralytics (images/labels × train/val + data.yaml, split determinista por hash, nombres tienda__ciudad__fecha__page_NN), listo para entrenar el YOLO unificado (todas las tiendas en un solo modelo) cuando haya volumen suficiente (~50–150 páginas anotadas).

Capa VLM abstracta (sina/vlm/): VLMProvider (ABC) + OllamaVLMProvider (visión local, salida estructurada con format=<json schema>) + fábrica get_vlm_provider() gated por ENABLE_VLM. Mismo patrón que el LLM del chat: un patrocinador añade un GeminiVLMProvider sin tocar el pipeline.

3.8. Mapa de almacenamiento — dónde vive cada dato

Cuatro backends conviven, cada uno con un criterio claro. Regla general: Postgres para el dominio relacional/consultable, Mongo para lo documental que cambia en runtime (siempre degradable — la app funciona con Mongo caído), filesystem para artefactos que acompañan a archivos (imágenes de flyers) y git para configuración que es parte del código.

Dato Dónde vive Quién escribe Notas
Precios (gasolina, gas LP, supermercados) Postgres Scrapers + scheduler + anotador (persistir) Fuente de verdad del dominio.
Catálogos geográficos CNE Postgres sina.db.seeder (manual) Seed desde datos/gasolineras/catalogo_municipios.json (estático, generado en notebook).
Rutas de scraping por tienda Postgres (catalogos_config) Seeder desde config/*_config.json Los JSON son la semilla versionada; el runtime lee Postgres.
Usuarios (Google OAuth) Postgres (usuarios) Login / PATCH /me Sin contraseñas ni tokens.
Sesiones Cookie firmada (sina_session, HMAC) Backend al login Stateless: no hay tabla ni colección de sesiones.
Historial de chat + telemetría por mensaje Mongo (conversaciones, chat_chunks) POST /chat al completar el stream Solo usuarios con sesión; anónimos no persisten.
Ciudades de flyers añadidas en la UI Mongo (flyer_ciudades) POST /annotator/flyer (si la descarga funcionó) Semilla de solo lectura: config/flyer_ciudades.json.
Auditoría de jobs del scheduler Mongo (registro_jobs, TTL 90 días) Wrapper _con_registro en scheduler.py GET /api/v1/annotator/jobs (admin).
Artefactos de flyers (imágenes, metadata/labels/extraccion/persistido.json, labels_yolo/) Filesystem datos/flyers/<tienda>/<ciudad>/<fecha>/ Spiders + endpoints del anotador A propósito NO van a Mongo: acompañan a las imágenes que describen y el ciclo de vida debe funcionar aunque Mongo esté caído.
Dataset YOLO consolidado Filesystem datos/yolo_dataset/ python -m sina.annotator.dataset Derivado; se reconstruye completo en cada corrida.
Configs (clases, ciudades semilla, rutas de tiendas) Git (src/sina/config/*.json) El desarrollador (commit) Configuración = código; no se muta en runtime.
Preferencias del visitante (tema, ubicación) Navegador (localStorage: sina.theme, sina.ubicacion) La SPA Por-dispositivo. Migrarlas a Mongo por usuario es candidato futuro, igual que una “lista de compras” persistente (feature nueva, no migración).
Clave admin del anotador Navegador (sessionStorage) La UI del anotador Secreto de dispositivo; jamás se persiste server-side.

Deprecado/legacy (documentado para no confundir): tabla Postgres chat_historial (el chat vive en Mongo) y sina/ollama/extract_flyer_text.py → flyer_data.json (sustituido por vlm/extraccion.py → extraccion.json).
