Despliegue y Operación

8.1. Requisitos

  • Python ≥ 3.12 con uv como gestor de paquetes.
  • Podman (para levantar PostgreSQL + pgvector y MongoDB vía compose.yaml).
  • Ollama con el modelo multimodal del proyecto (qwen3.6:35b: chat + VLM de flyers) y el de embeddings (qwen3-embedding:8b).
  • Node (para construir la SPA en frontend/).

8.2. Correr en local

uv sync                                       # instala dependencias
podman-compose up -d                          # PostgreSQL 16 + pgvector + MongoDB
uv run python -m sina.db.seeder               # catálogos + rutas de scraping
uv run uvicorn sina.main:app --reload         # servidor de desarrollo en :8000

Para el chat (Fase 3):

ollama pull qwen3.6:35b                        # multimodal: chat (tools) + VLM de flyers
ollama pull qwen3-embedding:8b                 # embeddings (búsqueda semántica)
ollama pull qwen3.5:9b                         # clasificador de moderación (opcional)
# .env → ENABLE_CHAT=1  (+ ENABLE_MODERACION=1 para la capa de moderación)

Frontend (SPA):

cd frontend
npm install
npm run dev        # desarrollo
npm run build      # producción (la sirve FastAPI en el mismo origen)

Recordatorio (gotcha). Define el .env (copiado de .env.example) antes de importar cualquier módulo bajo sina.db: el destino de la base de datos se fija en import-time (ver Arquitectura §2.5).

8.3. Base de datos con Podman: persistencia, ciclo de vida y acceso

compose.yaml levanta dos contenedores: PostgreSQL 16 + pgvector (sina_db, puerto host 5433) y MongoDB (sina_mongo, puerto 27017). Se usa la imagen pgvector/pgvector:pg16 a propósito: trae la extensión pgvector que SINA necesita para los embeddings; un PostgreSQL instalado de forma nativa no la trae y habría que compilarla aparte. Por eso el contenedor es la vía recomendada sobre una instalación nativa (para la app da igual: se conecta al localhost:puerto del .env).

Tres cosas con ciclos de vida distintos. La confusión típica es creer que apagar el contenedor borra los datos. No:

Cosa Qué es Cuándo se borra
Imagen (pgvector/pgvector:pg16) El “molde”; se descarga una sola vez Solo con podman rmi. Nunca por apagar/reiniciar.
Contenedor (sina_db) La instancia en ejecución Solo con podman-compose down (o podman rm).
Volumen (sina_pgdata) Los datos de PostgreSQL Solo con podman-compose down -v o podman volume rm.

Los datos viven en el volumen nombrado sina_pgdata (y sina_mongodata para Mongo), no dentro del contenedor → sobreviven a stop, a down (sin -v) y a reinicios de la PC.

Comandos de operación:

podman-compose up -d      # crea/levanta los contenedores en segundo plano
podman-compose stop       # los pausa (conserva contenedor + datos) — lo más suave
podman-compose start      # los vuelve a arrancar
podman-compose down       # borra los CONTENEDORES; CONSERVA los datos (volumen)
podman-compose down -v    # ⚠️ borra contenedores Y DATOS (volúmenes)
podman ps                 # ver qué está corriendo ahora
podman ps -a              # incluir los detenidos

Al reiniciar la PC (Windows/WSL). Podman corre dentro de una máquina WSL (podman-machine-default). Al apagar el equipo, esa máquina se detiene y con ella los contenedores. El servicio podman-restart está habilitado dentro de la máquina (jul 2026: podman machine ssh "sudo systemctl enable --now podman-restart"), así que el restart: unless-stopped del compose.yaml revive los contenedores solo con que la máquina arranque. En Windows esa máquina no siempre arranca sola tras un reinicio; regla práctica: tras reiniciar, corre podman ps; si sina_db/sina_mongo no aparecen en Up:

podman machine start      # arranca la máquina WSL; podman-restart revive los contenedores
podman ps                 # confirmar sina_db (5433) y sina_mongo (27018) en Up

Ver los datos con una GUI (no es solo CLI). Como el contenedor publica el puerto a tu equipo (5433:5432), para cualquier cliente es un PostgreSQL normal en localhost. Sirven pgAdmin, DBeaver, DataGrip, TablePlus o la extensión PostgreSQL de VS Code. Parámetros de conexión (los mismos del compose.yaml / .env):

Campo Valor
Host localhost
Puerto 5433
Base de datos sina_db
Usuario sina_admin
Contraseña sina_password

psql (CLI) funciona igual pero es opcional. Para Mongo, misma idea en localhost:27018 (el puerto del contenedor de SINA — ver el aviso de arriba) con MongoDB Compass.

Puertos en la máquina de desarrollo: por qué SINA usa 5433 y 27018

SINA está basado en sus contenedores, pero la app se conecta a lo que responda en el puerto de localhost, y en esta máquina los puertos estándar están ocupados por servicios de otros proyectos que sombrean a los contenedores de SINA (pasó dos veces en jul 2026: los datos acababan en la instancia equivocada). Resolución permanente — cada proyecto su puerto, sin tocar los servicios ajenos:

Puerto Quién Nota
27017 MongoDB 8 nativo de Windows (otros proyectos) No tocar.
27018 sina_mongo (contenedor, MONGO_URI=mongodb://localhost:27018) El de SINA.
5432 argos-postgres (contenedor de otro proyecto, también con restart automático) No tocar.
5433 sina_db (contenedor, DB_PORT=5433) El de SINA.

Si algo se ve raro (datos que “no aparecen”), verifica qué instancia responde:

podman ps --format "{{.Names}} {{.Ports}}"                     # puertos publicados por contenedor
podman exec sina_mongo mongosh --quiet --eval "db.version()"   # contenedor Mongo de SINA → 7.x
podman exec sina_db psql -U sina_admin -d sina_db -c "SELECT version();"

Consultas rápidas sin instalar clientes (usando los CLI que ya traen los contenedores — válido cuando los contenedores SON quienes sirven los puertos):

# ── PostgreSQL (psql dentro del contenedor) ──────────────────────────
podman exec -it sina_db psql -U sina_admin -d sina_db
#   \dt                             → listar tablas
#   SELECT COUNT(*) FROM supermercados WHERE fuente='flyer';
#   SELECT tienda, COUNT(*) FROM supermercados GROUP BY tienda;

# ── MongoDB (mongosh dentro del contenedor) ──────────────────────────
podman exec -it sina_mongo mongosh sina
#   show collections                → conversaciones, chat_chunks, flyer_ciudades, registro_jobs
#   db.conversaciones.find().sort({actualizado_en:-1}).limit(5)     → últimos chats
#   db.chat_chunks.countDocuments()                                 → volumen de mensajes
#   db.flyer_ciudades.find().sort({nombre:1})                       → ciudades añadidas en la UI
#   db.registro_jobs.find().sort({inicio:-1}).limit(10)             → últimas corridas de jobs
#   db.registro_jobs.find({ok:false})                               → corridas fallidas
#   db.registro_jobs.find({job:"flyers"}).sort({inicio:-1})         → historial del monitor de flyers
#   db.stats()                                                      → tamaño de la base

# ── Respaldos ────────────────────────────────────────────────────────
podman exec sina_db pg_dump -U sina_admin sina_db > respaldo_sina.sql
podman exec sina_mongo mongodump --db sina --archive > respaldo_mongo.archive
# restaurar:
#   Get-Content respaldo_sina.sql | podman exec -i sina_db psql -U sina_admin -d sina_db
#   Get-Content respaldo_mongo.archive -Raw -Encoding Byte | podman exec -i sina_mongo mongorestore --archive

El mapa completo de qué dato vive en qué backend (Postgres/Mongo/filesystem/git/navegador) y por qué, está en Datos §3.8.

8.4. Configuración (.env)

Variables clave (ver .env.example para la lista completa):

Grupo Variables
Base de datos DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD (si faltan host/name/user/password → SQLite fallback). Ver §8.3.
Scraping (URLs base) SORIANA_BASE_URL, DELSOL_BASE_URL, BENAVIDES_BASE_URL, GUADALAJARA_BASE_URL
Chat / LLM ENABLE_CHAT, LLM_PROVIDER, OLLAMA_HOST, OLLAMA_MODEL, LLM_TEMPERATURE, LLM_MAX_ITERS
Moderación del chat ENABLE_MODERACION, MODERACION_MODEL, MODERACION_HOST (vacío = OLLAMA_HOST), MODERACION_TIMEOUT_S — ver Agente §5.8
Embeddings ENABLE_EMBEDDINGS, EMBEDDING_MODEL
MongoDB (chat) MONGO_URI, MONGO_DB, CHAT_MAX_CONVERSACIONES, CHAT_CHUNK_SIZE
Scheduler ENABLE_SCHEDULER, ENABLE_SUPERMERCADOS_SCRAPING
Seguridad / auth GOOGLE_OAUTH_CLIENT_ID, ADMIN_API_KEY, allowlist de CORS

8.5. Operación

  • Scheduler (ENABLE_SCHEDULER=1): gasolina diario 06:00, gas LP sábados 08:00 (hora MX); supermercados semanal opt-in (ENABLE_SUPERMERCADOS_SCRAPING).
  • Health check: GET /api/v1/health reporta la última actualización y la vigencia por categoría.
  • Degradación elegante: si MongoDB no está, el chat funciona sin persistencia (y la moderación clasifica pero no persiste strikes); si el clasificador de moderación falla o excede su timeout, la consulta pasa (fail-open); si los datos de gobierno fallan, se sirve caché vencida con aviso (fuente = cache_vencido).
  • Tests: uv run pytest tests/ -q (suite de la capa de moderación).

8.6. Empaquetado (meta)

  • Podman, no Docker. Containerfile para el backend; compose.yaml para app + PostgreSQL/pgvector (+ MongoDB). (Fase 5, pendiente.)

8.7. Estrategia de despliegue en GCP (objetivo)

El flujo extraer → limpiar → guardar → servir UI encaja bien en un modelo serverless:

  • Backend + SPA: Cloud Run.
  • Base de datos: Cloud SQL (PostgreSQL con pgvector).
  • Scraping / refresco: Cloud Scheduler → Cloud Run Jobs.
  • Secretos: Secret Manager.

Destinos posibles: PC local, servidor dedicado (mismo contenedor) y GCP (meta). Falta conseguir patrocinador para servidor/dominio.
